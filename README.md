# Order Pad

A multi-tenant order/receipt pad for FiveM restaurant RP. Cashiers tap menu
buttons to build an order and copy a formatted receipt; each shop's owner
edits their menu live, and every device with the shop link sees updates in
real time.

## How it works

- **Shops** live at `?shop=<slug>`. Anyone with the link can take orders.
- **Owners** unlock menu editing with the shop passcode (🔒 button).
- **New shops** are created from the landing page with a one-time invite code.
- **Invite codes** are generated by the admin from the landing page (🔑 Admin).
- **Local mode** (`?local=1` or a `?template=` link) works fully offline with
  no shop — the original Order Pad behavior.

Data is stored in Firebase Realtime Database (`orderpaddb`) over its REST
API — no Firebase SDK. Live menu updates stream over SSE. Only the menu is
shared; in-progress orders stay on the device.

### Database layout

```
/admin/passcode            { hash, salt }          write-once (set on first admin login)
/inviteCodes/{CODE}        { created, usedBy, usedAt }
/shops/{slug}/
    name, created, lastSeen, inviteCode
    passcode               { hash, salt }          owner passcode
    menu/
        _version           sync counter (ETag CAS)
        title, stylePreset
        groups, items, specials
```

## Development

```bash
npm install
npm run dev        # http://localhost:8080
npm run build      # production build → dist/
```

Vanilla ES modules, no framework. Vite bundles; GitHub Actions builds and
deploys `dist/` to GitHub Pages on every push to `main` or `Backend-Version`.

## Firebase database rules

The rules the database must run with are in [`database.rules.json`](database.rules.json).
Paste them into **Firebase console → Realtime Database → Rules → Publish**.

What they enforce (and what they can't):

- The admin passcode node is **write-once** — after the first admin login sets
  it, it can only be changed from the Firebase console.
- Invite codes are **single-use at the database level**: a code's `usedBy` can
  only be written while it is empty, and codes can't be deleted (audit trail).
- A shop's `name`/`created`/`inviteCode` are **write-once**, and `name` can only
  be created when the referenced invite code was redeemed for that exact slug —
  you can't conjure a shop by guessing a URL.
- Everything else under a shop (menu, passcode) requires the shop to exist.

Because the app talks to the DB without Firebase Auth, the rules **cannot**
tell an owner from a visitor: anyone who knows a shop's slug could write to
its menu or passcode via the REST API directly. The passcode gate is a UI
gate. That matches the Commission-Tracker design this is based on; moving to
Firebase Auth + per-user rules is the upgrade path if it ever matters.
